HTTP ROOT CAUSE
---------------
Every .dev hostname is on Chrome's built-in HSTS preload list, including fly-analytics.fly.dev.
Chrome rewrites http://fly-analytics.fly.dev/... to https:// inside the browser, before any packet is sent.
DevTools shows this as "307 Internal Redirect" with "Non-Authoritative-Reason: HSTS".

The demo page sent Content-Type: application/json, which triggers a CORS preflight (OPTIONS).
Browsers do not allow a preflight to follow a redirect, so Chrome reported:
  "Response to preflight request doesn't pass access control check: Redirect is not allowed for a
   preflight request." (corsError PreflightDisallowedRedirect, net::ERR_INVALID_REDIRECT)
The page then showed "TypeError: Failed to fetch".

Ruled out:
  - Mixed content: the page is http://localhost:3000, so Chrome blocked nothing for mixed content.
  - Fly: `force_https = false` in fly.toml, and the deployed config has no force_https.
    curl gets OPTIONS 204 and POST 200 over plain HTTP, with no redirect.
  - CORS headers: HTTP and HTTPS both return Access-Control-Allow-Origin: *,
    Access-Control-Allow-Methods: POST, OPTIONS, and Access-Control-Allow-Headers: Content-Type.
  - Proxy: the web (HTTP) proxy was already OFF. The failure is identical with --no-proxy-server.
  - Network: a tshark capture during the click showed 0 packets to 66.241.125.201 on port 80 or 443.

Plaintext HTTP from Chrome to any *.dev host is therefore not possible.
The options were a dedicated Fly IPv4 (paid), a Chrome HSTS bypass policy (weakens security), or a custom domain.
The chosen fix: do not force browser plaintext.
  - The HTTP button is labelled as upgraded and sends a CORS "simple" request (text/plain, no preflight),
    so Chrome can follow its HSTS upgrade. It returns 200 OK and states the upgrade on the page.
  - The plaintext HTTP -> tshark path is tested with `python client.py http`, which does not apply HSTS.
Fly's free dedicated IPv6 (2a09:8280:1::19c:cd58:0) was not usable because this Mac has no working IPv6 route.

NOTES
-----
- Browser HTTP is HTTPS in practice. Anything Chrome sends to fly-analytics.fly.dev is encrypted,
  so tshark will never see it; only mitmproxy can. Plaintext HTTP capture needs a non-browser client such as client.py.
- The browser tests used headless Chrome with a fresh profile and the extension loaded through DevTools.
  Chrome 154 no longer honors --load-extension. They were not run in your normal Chrome window,
  but they use the same system proxy and the keychain-trusted mitmproxy CA.
- The extension records the HTTP button twice (lines 7 and 8): once for the original http:// URL
  and once after the internal HSTS upgrade. It also records localhost:3000 page and favicon loads,
  which the demo filter treats as relevant.
- Fly returned 502 for the gzip test request. fly-analytics/server.py decodes every body as UTF-8
  and fails on gzip bytes. This did not affect the collector; the event was stored correctly.
- local_api.py handles requests concurrently. When two extension events arrive together, their CLI
  cards can interleave in the terminal. The JSONL lines stayed intact (10/10 valid). This was not changed.
- The symptoms.* keys in the browser payload produce no findings, because the classifier matches the
  field name "symptom" only. This is unchanged.
